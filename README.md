# Adaptive Piston Algorithm

Adaptive Piston Algorithm is a pressure-slope based analysis workflow for detecting potential clogging events in fluid delivery systems. It monitors pressure traces, calculates sliding-window slopes, identifies trigger points, and estimates backflush intervals from configurable flow and volume parameters.

The code in this repository focuses on data analysis and demonstration workflows. Hardware communication with pumps, pressure sensors, and valves should be implemented in a separate control layer.

## Main Capabilities

- Pressure-trace analysis from simulated data or CSV input
- Sliding-window pressure slope calculation
- Trigger detection using slope threshold, grace period, and minimum trigger interval
- Backflush duration and interval calculation
- CSV export of trigger and backflush results
- Diagnostic plotting for pressure traces, slope traces, parameter sensitivity, and real-time simulation
- Basic, advanced, and reproducible-run examples

## Basic Python Usage

```python
from src.core import (
    calculate_backflush_duration,
    calculate_backflush_intervals,
    detect_triggers,
)
from src.data_processing import simulate_pressure_data

# Generate synthetic pressure data
timestamps, pressures = simulate_pressure_data(
    duration=120.0,
    sample_rate=1.0,
    baseline=100.0,
    noise_std=1.5,
    clog_events=[
        (25.0, 6.0, 35.0),
        (55.0, 7.0, 28.0),
        (85.0, 8.0, 32.0),
    ],
)

# Detect pressure-trigger events
triggers = detect_triggers(
    pressure_series=pressures,
    timestamp_series=timestamps,
    slope_threshold=20.0,
    grace_period=5.0,
    min_trigger_interval=13.0,
)

# Calculate backflush windows
backflush_duration = calculate_backflush_duration(
    backflush_volume_ml=0.1,
    backflush_flow_ml_hr=10.0,
)
results = calculate_backflush_intervals(triggers, backflush_duration)

print(f"Detected {len(triggers)} trigger(s)")
print(f"Backflush duration: {backflush_duration:.2f} s")
```

## Core Algorithm

### Sliding-window slope calculation

The default trigger detector uses a five-point sliding window. For each full window, it calculates the average pressure slope:

```text
average_slope = mean((p[i+1] - p[i]) / (t[i+1] - t[i]))
```

where `p` is pressure and `t` is timestamp.

### Trigger detection

A trigger is recorded when all of the following conditions are met:

1. The current timestamp is outside the startup grace period.
2. The sliding-window average slope is greater than or equal to the slope threshold.
3. The time since the last trigger is greater than or equal to the minimum trigger interval.

Each trigger is returned as:

```text
(trigger_time, data_index, average_slope)
```

### Backflush calculation

Backflush duration is calculated from volume and flow rate:

```text
backflush_duration_seconds = backflush_volume_ml / backflush_flow_ml_hr * 3600
```

For each trigger, the backflush interval is reported as:

```text
[trigger_time, trigger_time + backflush_duration_seconds]
```

## Data Format

CSV input can contain either two columns or one column.

### Two-column CSV

```csv
time,pressure
0.0,100.2
1.0,101.5
2.0,102.8
```

### One-column CSV

```csv
pressure
100.2
101.5
102.8
```

When only pressure values are provided, timestamps are generated automatically at 1 Hz.

The real-time simulation processes pressure data in chunks. The first chunk uses the configured startup grace period, while later chunks use a zero-second grace period so that trigger detection is not restarted unnecessarily for each incoming chunk.

## Output Tables

Typical CSV outputs include:

```text
trigger_time,data_index,average_slope,backflush_start,backflush_end
```

These fields describe when the trigger occurred, where it appeared in the pressure series, the slope that caused the trigger, and the corresponding backflush interval.

## Notes

- Simulated data is intended for workflow demonstration and parameter testing.
- Real experimental use should provide measured pressure data through the `--csv` option.
- Hardware actuation is outside the scope of this repository and should be handled by a separate device-control layer.
